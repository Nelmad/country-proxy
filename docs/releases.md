# Версии и релизы Country Proxy

Короткая ветка → PR и проверки → `main`. Релиз выпускается по завершении полезного
этапа с пройденной приёмкой. Обычные исправления и документация накапливаются в
`Unreleased`; commit или PR не требуют отдельного релиза. Срочный PATCH оправдан
для существенного дефекта уже опубликованной версии.

## Версия и комплект

Источник версии — `extension/manifest.json`. Расширение, Python helper,
установщик и зависимости выпускаются одним комплектом. Расширение и помощник
при запуске проверяют поддержку протокола подтверждений замены. При несовпадении
расширение блокирует маршрут и предлагает обновить обе части из одного комплекта.

Используем `MAJOR.MINOR.PATCH` на основе [SemVer](https://semver.org/):

| Изменение | Номер |
| --- | --- |
| Совместимые исправления | PATCH: 0.2.0 → 0.2.1 |
| Новая возможность или изменение пользовательского/Native Messaging договора в 0.x | MINOR: 0.2.1 → 0.3.0 |
| Принятый стабильный договор эксплуатации | 1.0.0 после отдельной приёмки |
| Несовместимое изменение после 1.0 | MAJOR: 1.x → 2.0.0 |

В 0.x совместимость не подразумевается автоматически; изменения настроек и
миграции описываются явно. Manifest содержит три числа 0–65535, без ведущих
нулей, не все нули — по ограничениям [Chrome](https://developer.chrome.com/docs/extensions/reference/manifest/version).
Тег выпуска — `vX.Y.Z`; дата в CHANGELOG появляется при подготовке выпуска.
Для preview допустим тег `vX.Y.Z-rc.1` и такая же строка в `version_name`, но
числовое `version` остаётся `X.Y.Z`. Preview отмечается как GitHub Pre-release;
его ZIP различается с финальным выпуском по тегу и checksum, а не имени файла.

## Проверки и автоматизация

[CI](../.github/workflows/checks.yml) запускает offline contract на PR, push в main
и вручную. Права — только чтение; установки приложения, публичных прокси и
публикации нет. Локальные команды и браузерные стенды — в [CONTRIBUTING](../CONTRIBUTING.md).
Актуальные результаты, включая статус hosted CI, — в [verification](verification.md).

Оба workflow закрепляют один предварительно проверенный digest
`project-checks.json`. Локальный offline contract проверяет их согласованность
с точными байтами контракта; при его изменении нужно проверить команды и обновить
оба статических значения по [CONTRIBUTING](../CONTRIBUTING.md).
Такая проверка не означает, что workflow уже выполнен на GitHub.

[Prepare draft release](../.github/workflows/release-draft.yml) запускается только
вручную из `main` для уже существующего тега и проверенного commit. Он собирает
комплект и создаёт неопубликованный Draft Release. Сейчас workflow проверен
локально; запуск на GitHub ещё не выполнен. Настройки branch protection и
immutable releases включаются отдельно. Цели и приоритеты остаются в базе знаний.

## Приёмка выпуска

Для первого stable зафиксированы [возможности, договор настроек и конечная
матрица готовности](stable-readiness.md). Документ отделяет технический минимум
версий от фактически проверенных сочетаний и не является разрешением публикации.

| Изменение | Требуемые проверки |
| --- | --- |
| Любой выпуск | Offline contract, версия, документация, чистый reviewed commit, ZIP/checksum |
| Session, routing, browser probe, резерв | Fresh Chrome с резервом; restart и отказ browser route; отказ без резерва; блокировка direct; stop/смена страны |
| Установщик, зависимости, storage или путь helper | Установка, обновление и откат в отдельном профиле; сохранение стран/ID и работа helper |
| Источники или критерии адреса | Ограниченный публичный smoke с датой и фактическим результатом |
| Только документация/CI/упаковка | Проверки затронутых документов/инструментов/артефакта; без повторения неизменённых браузерных сценариев |

Перед первым оформленным выпуском обязательна проверка установки, обновления и
отката на macOS по [инструкции](installation.md). Для 1.0 дополнительно нужны
стабильный договор настроек/помощника, повторяемая приёмка и длительный прогон
с заранее определённым сроком и числом отказов.

Доступность публичных стран проверяется отдельно от механизма замены. Исправление
механизма можно выпустить с указанным ограничением доступности; `PARTIAL` не
становится `PASS`. Стенд с общим внешним IP не доказывает публичную пару NO/EE.
Ни один номер версии не гарантирует наличие бесплатных прокси.

## Выпуск

1. Выбрать законченный состав изменений и номер. Завершить применимую приёмку,
   review и CHANGELOG: раздел `## [X.Y.Z] - YYYY-MM-DD` (для preview — `X.Y.Z-rc.N`).
   `Unreleased`, пустой раздел и TODO не допускаются. Подробности и ограничения
   оформить по [шаблону](release-notes-template.md).
2. Зафиксировать точный commit **R** и предыдущую версию **B**. R должен попасть
   в `main`; если merge изменил код, повторить затронутые проверки. После решения
   о подготовке выпуска создать и отправить тег `vX.Y.Z` на R отдельным действием.
3. В Actions запустить **Prepare draft release** из `main`: существующий `tag`,
   полный 40-символьный `approved_sha` R, `acceptance_confirmed=true` после приёмки.
   Workflow проверяет tag → R и принадлежность R истории main; выполняет offline
   contract; сверяет исходники до/после тестов, ZIP/inventory/checksum. Отдельный
   job создаёт **draft** с ZIP, checksum и notes. Он не создаёт тег, не заменяет
   существующий Release и не публикует его. При частичном сбое проверить оставшийся
   draft; автоматического удаления или перезаписи нет.
4. Проверить draft, ограничения, assets/checksum и ссылки на инструкции именно
   для этого тега. Сборочные guards не заменяют браузерную приёмку; checkbox —
   подтверждение сопровождающего. Публикация выполняется отдельным действием;
   `Latest` — только для выбранного стабильного выпуска.
5. Проверить опубликованные ссылки и checksum. Установка пользователем выполняется
   отдельно по [инструкции](installation.md); Release не обновляет Chrome автоматически.

Для локальной сборки без GitHub используйте `python3 scripts/package.py`:
`dist/country-proxy-X.Y.Z.zip` и `.zip.sha256`. GitHub Source code ZIP — другой архив.

Сборщик нормализует порядок, время и права ZIP; при одинаковых исходниках и версии
Python/zlib архив повторяем. Inventory содержит SHA-256 файлов, но сборщик не
проверяет Git history: `local-working-tree` и `release_verified: false` сохраняются.
Соответствие R подтверждается отдельно; одна успешная сборка не означает релиз.
При изменении поставляемых байтов после проверки повторяются затронутые проверки
и сборка. Не перезаписывайте уже выданный кандидат без сохранения старой копии.

Опубликованные теги и assets не заменяются. Исправления накапливаются до следующего
выпуска с новым номером; для отката используется предыдущий проверенный комплект.
Подробности GitHub: [releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)
и [публикация draft](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository).
