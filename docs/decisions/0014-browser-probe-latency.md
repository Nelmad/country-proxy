# 0014 — Ограниченный дополнительный HTTPS-запрос в Chrome

Принято 14 ноября 2026 года. Дополняет
[параллельный поиск при восстановлении](0013-parallel-recovery-discovery.md).

В публичном наблюдении браузерное подтверждение заняло около 20 секунд.
Встроенного таймера такой длины нет; оба HTTPS-контроля уже выполнялись
параллельно. У повторно наблюдённой задержки 17,712 секунды CDP показал большую
часть ожидания до TLS, при почти немедленном запуске fetch контроллером.
Эти интервалы сами по себе не разделяют TCP, DNS и SOCKS negotiation.
Точный старый 20-секундный запрос не сохранён, его причина не устанавливается
задним числом по новому наблюдению.

Для ещё ожидающего ответа origin после пяти секунд запускается ровно один
дополнительный fetch. Он использует тот же прокси, HTTPS-сервис и политику
сертификатов, без credentials/cache/redirect. Исходный fetch не отменяется до
успеха или окончательного отказа. Общий предел — два запроса на origin и четыре
на probe, без продления исходного 50-секундного deadline.

По-прежнему необходимы Cloudflare HTTP 200 с валидным IP и страной из
равноправного выбранного набора и Google HTTP 204. Это не гонка между странами
и не обход проверки второго сервиса. Исходный отказ остаётся немедленно
фатальным. Только транспортный отказ необязательного дополнительного запроса
не отвергает ещё работающий исходный запрос. Неверный HTTP/trace/country,
полученный до завершения соответствующего контроля, отвергает весь probe.
После завершения контроля его лишние запросы отменяются; запоздалый результат
ничего не подтверждает. Общая отмена, смена поколения и потеря маршрута
сохраняют прежние проверки контроллера.

Параллельные сигналы перепроверки одного актуального предложения объединяются
лишь пока его сеть ещё проверяется или такая проверка уже поставлена в очередь.
Ключ включает поколение, attempt, proxy endpoint, native exitIp/country и набор
разрешённых стран. Отдельного кэша готовых результатов нет: сигнал после
окончания HTTPS начинает новую проверку. Это устраняет отдельную очередь
повторных probe, но не объясняет исходную задержку первого подключения.

Chrome может выполнить исходный fetch через соединение, открытое дополнительным
запросом. Поэтому номер победившего запроса и число открытых туннелей — разные
факты. AbortSignal отменяет запрос, но не гарантирует немедленный TCP EOF у
внутреннего ConnectJob. Локальная приёмка сохраняет оба наблюдения отдельно.
В HTTP 204 достаточно успешных заголовков; последующая отмена ненужного body
не превращает уже проверенный 204 в сетевой отказ.

Это ограниченное увеличение нагрузки только для медленных контролей.
Быстрый успешный probe остаётся двумя запросами. Изменения не дают новых
разрешений, не меняют native-проверки, выбор стран, бюджет поиска, таймауты
health или правила резерва. Стендовые результаты не обещают пятисекундную
замену на публичных прокси; доступность и скорость проверяются отдельно.
