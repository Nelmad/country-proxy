# ADR 0004 — Ручная подготовка черновика релиза

Дата: 2026-10-30. Статус: принято для реализации; hosted workflow ещё не запускался.
Дополняет [ADR 0003](0003-release-process.md).

## Контекст

Обычные изменения накапливаются в `Unreleased`. Выпуск нужен после завершённого
полезного этапа и применимой приёмки, а не для каждого commit или PR. Повторяемые
проверки и упаковку стоит автоматизировать, сохранив отдельное решение о публикации.

## Решение

`Prepare draft release` запускается только вручную с `main`. Сопровождающий задаёт
существующий тег, полный одобренный SHA и явно подтверждает завершение приёмки.
Workflow не создаёт тег, не меняет номер версии и не финализирует CHANGELOG сам.

Два jobs имеют разные полномочия:

1. **Build — contents: read.** Через GitHub API проверить tag → SHA и принадлежность
   SHA истории `main`; отказаться при существующем Release. Checkout выполняется
   по точному SHA без сохранённых credentials. До тестов фиксируются хеши поставляемых
   файлов. После reviewed offline contract проверяются неизменность исходников,
   версия/CHANGELOG, состав ZIP и checksum. Архив, notes и metadata передаются
   артефактом текущего запуска; их SHA передаются отдельно через job outputs.
2. **Draft — contents: write.** Нет checkout и выполнения кода из скачанного
   артефакта. Закреплённый workflow проверяет хеши по outputs первого job,
   inventory ZIP и ещё раз tag → SHA / `main` / отсутствие Release. Затем создаёт
   только draft с `--verify-tag --latest=false`; RC получает `--prerelease`.

Опубликование, выбор Latest, обновление Chrome и изменение существующих assets
не входят в этот workflow. Ошибка загрузки может оставить частичный draft;
его сначала проверяют вручную, повторный запуск не перезаписывает его.

## Границы проверки

Offline CI не подтверждает браузерную приёмку, живые публичные прокси или отсутствие
секретов в Git history. Это отдельные проверки до решения о выпуске. ZIP сохраняет
честную отметку сборщика `local-working-tree` / `release_verified: false`;
соответствие выбранному SHA проверяет workflow поверх inventory.

Права, branch protection и неизменяемость опубликованных тегов/releases
настраиваются отдельно. Присутствие YAML не включает эти настройки.

## Проверка реализации

Локально проверяются парсинг YAML, синтаксис Bash/Python, source/ZIP mutation gates
и точные inline API guards на искусственных ответах. Реальные GitHub calls,
создание draft и загрузка assets подтверждаются только будущим отдельным ручным
запуском после отправки согласованного commit и тега.
