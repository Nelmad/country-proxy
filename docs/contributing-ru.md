# Разработка Country Proxy

[English contributor entry](../CONTRIBUTING.md). Все команды ниже выполняются из корня репозитория.

Начните с [AGENTS.md](../AGENTS.md), [архитектуры](architecture.md) и
[контракта проверок](../project-checks.json). Код расширения находится в `extension/`,
помощник — в `native/`, проверки — в `tests/`.

## Рабочая копия

Используйте короткую ветку `codex/<задача>` от актуального `main` и отдельную
рабочую копию. Не разрабатывайте в папке, из которой основной Chrome запускает
помощник: изменения Python начинают действовать при следующем его запуске даже
без обновления UI. Не перезаписывайте чужие незакоммиченные изменения.

## Локальные проверки без сети

Python 3.11+; рекомендуемый Node — 24 LTS. Текущие unit/structure checks не требуют
установки proxy-scraper, запуска Chrome или обращения к публичным прокси.
Если используете уже подготовленное окружение, активируйте его:

```sh
source .venv/bin/activate
python3 scripts/check.py --list
```

Прочитайте `project-checks.json`, сверьте список и выполните:

```sh
python3 scripts/check.py --execute-reviewed <digest-из-предыдущего-шага>
```

`--list` ничего не запускает. При изменении контракта digest меняется: новую
команду нужно проверить, а не автоматически подставлять вычисленное значение.
После review закрепите одно и то же статическое значение в
`.github/workflows/checks.yml` и `.github/workflows/release-draft.yml`.
Не вычисляйте разрешающий digest внутри workflow: это отменило бы проверку
предварительно утверждённого контракта.

Регрессия `tests/test_workflow_contract.py` входит в обычный offline contract
через unittest discovery. Она сверяет оба значения с точными байтами файла и
проверяет исполняемый шаг, исключая подстановку, комментарий и неоднозначные
команды. Формат намеренно ограничен: обычные отображения `jobs`/job/`steps`
с простыми ASCII-ключами, а у проверяемого шага — имя и однострочный `run` с
буквальным digest, без дополнительных атрибутов. Изменение этого формата
требует review и соответствующего изменения регрессии.

CI `Offline checks` запускает этот контракт на Ubuntu 24.04, Python 3.11 и
Node 24. Actions закреплены по SHA; токен имеет только чтение. CI не устанавливает
приложение, не вызывает открытые прокси, не собирает и не публикует релизы.
Успех этого job не заменяет локальный браузерный тест на macOS.

## Проверка окна расширения

В распакованном комплекте выполните четыре сценария с Chrome for Testing и Playwright:

```sh
node tests/ui-layout-lab.mjs
node tests/ui-keyboard-lab.mjs
node tests/saved-groups-lab.mjs
node tests/group-backup-lab.mjs
```

Каждый сценарий использует собственный профиль. Для штатного окна стенд вызывает
`chrome.action.openPopup()`; для воспроизводимых крайних случаев задаёт размер
окна, размер шрифта Chrome и состояние расширения. Клавиатура, кнопки, загрузка
файла и изменения в Chrome Storage проверяются в браузере. Перенос требует двух
независимых профилей. Эти сценарии не измеряют доступность публичных адресов.
Результаты и снимки остаются в `.runtime/`.

## Измерение поиска и восстановления

Перепроверку резерва помощником проверяет стенд с настоящим curl и Chrome:

```sh
node tests/native-reserve-latency-lab.mjs
```

Он использует временные профили Chrome for Testing, локальные CONNECT/HTTPS
и синтетический равноправный набор AT/EE/NO. Один native CONNECT удерживается
до TLS; отдельно измеряются native-подтверждение и работа Chrome. Прежний
код проверяется тем же harness через `TEST_SOURCE_ROOT`; `TEST_PYTHON` и
`PLAYWRIGHT_MODULE` указывают существующее окружение. Проверяются также
HTTP/TLS/страна, обязательность второго сервиса, Stop и смена группы,
пополнение после замены и повторный физический отказ. Основной Chrome
не используется. Результаты остаются в `.runtime/`.

В публичном групповом отчёте native recheck может содержать ограниченную
численную проекцию отдельных curl. Она связана с реально возвращённым report;
при отмене без результата остаётся неизвестной. Нулевое/отсутствующее curl timing
не доказывает сетевую фазу. Этот QA-наблюдатель не сохраняет URL, IP, headers
или body и не участвует в принятии адреса.

Задержку браузерного подтверждения проверяет отдельный стенд:

```sh
node tests/browser-latency-lab.mjs
```

Временный Chrome for Testing использует реальные HTTPS и SOCKS4/CONNECT с
локальными серверами и синтетической географией AT/EE/NO. Семь сценариев
проверяют зависшее рукопожатие, объединение одновременных перепроверок, отказ
HTTP/TLS/страны, отключение и смену группы. `TEST_SOURCE_ROOT` позволяет
применить тот же harness к прежнему снимку; нужны `PLAYWRIGHT_MODULE` и Chrome
for Testing. Стенд использует настоящий Controller/probe с заданными native
событиями; он не заменяет проверку всего помощника и background в
`tests/resilience-group-local.mjs`. Дополнительный запрос может открыть новый
туннель, которым Chrome завершит исходный запрос; победитель определяется по
наблюдаемому request ordinal, а не угадывается. Отмена fetch не означает
немедленное закрытие внутреннего TCP ConnectJob браузера.

Публичный `tests/public-group-failover.mjs` сохраняет обезличенные интервалы
успешных подтверждений и точные номера их HTTPS-запросов. Для ограниченной
локализации до TLS есть отдельный `tests/browser-latency-netlog.mjs`: один
проход до 90 секунд / 120 проверок, без инъекции отказа. Сырой NetLog и профиль
удаляются; отчёт содержит только разрешённые числовые интервалы связанных
событий. Отсутствие успешной пары означает INCONCLUSIVE. Не складывайте сырые
сетевые логи в репозиторий.

Параллельный поиск при проверке резерва и пополнение после замены:

```sh
node tests/parallel-recovery-lab.mjs
```

Стенд использует отдельные временные профили Chrome for Testing, локальные
CONNECT/HTTPS-серверы и синтетическую географию AT/EE/NO. Он проверяет оба исхода
гонки, пополнение после подтверждения Chrome, второй отказ и отключение во время
проверок. Первый переход запускается явной командой замены: его время показывает
работу подбора, а не обнаружение сетевого отказа. Для сравнения с сохранённым
снимком задайте `TEST_SOURCE_ROOT=/absolute/path/to/snapshot`; сам стенд остаётся
одинаковым. `TEST_PYTHON` задаёт Python существующего тестового окружения,
`PLAYWRIGHT_MODULE` — установленный Playwright. Основной Chrome не используется.
Результаты, временные границы и ограничения — в локальном `.runtime/`.

Причины снятия резерва проверяются отдельно:

```sh
node tests/reserve-removal-lab.mjs
```

Стенд использует временный Chrome for Testing, локальные HTTPS-сервисы и одну
равноправную группу AT/EE/NO. Сетевые ошибки воспроизводятся ответом HTTP 503
и недоверенным сертификатом; истечение срока и страна вне группы задаются
контролируемыми состояниями записи. Проверяются также успешная и отменённая
перепроверки, обычная HTTPS-вкладка и отображение причин. Основной Chrome и
публичные прокси не используются. Требуются те же Playwright и Chrome for Testing,
что для остальных браузерных стендов; отчёт остаётся в `.runtime/`.

Перед изменением алгоритма сохраните snapshot исходников вне Git и используйте
[замороженный контракт](decisions/0007-recovery-measurement-contract.md):

```sh
python3 -B tests/recovery_benchmark.py --root /absolute/path/to/snapshot --contract tests/recovery-contract.json --repeats 20 --output /absolute/path/to/local/native.json
node tests/controller-benchmark.mjs --root /absolute/path/to/snapshot --repeats 20 --output /absolute/path/to/local/controller.json
```

Стенды вызывают настоящий код с искусственными входами, без сети и Chrome.
Одинаковые harness/config применяются до и после изменения. В отчёте отдельно
считаются ошибки, timeout и invalid; успешные latency не скрывают эти исходы.
Это описательные измерения стенда, а не скорость публичных прокси.
Обычный unit runner проверяет [модель равноправия](recovery-fairness.md)
и независимо фиксирует фактические старты проверок в рабочем планировщике.

Для замеров холодного поиска с быстрым и медленным источниками запустите одну и
ту же [проверку порядка событий](../tests/stream-timing.py) против старого и нового
снимков в отдельных процессах. Она подменяет сеть, но использует обычный `Session`:

```sh
python3 -B tests/stream-timing.py --root /absolute/path/to/snapshot --output /absolute/path/to/local/stream.json
```

Для истории отдельно сравниваются число физических проверок и обнаружение
восстановленного адреса при одинаковом расписании. Проверка установленного
launcher использует готовый venv и читает предыдущий комплект для отката.

```sh
python3 -B tests/history-benchmark.py --before /absolute/path/to/previous-snapshot --output /absolute/path/to/local/history.json
TEST_BASELINE_ROOT=/absolute/path/to/previous-bundle .venv/bin/python -B tests/install-runtime.py
```

Для сравнения порядка источников используйте один и тот же стенд на двух
снимках. Он записывает исходные условия до обучения и отдельно оценивает
рабочие адреса и покрытие стран на семи сценариях.

```sh
python3 -B tests/source-quality-benchmark.py --before /absolute/path/to/previous-snapshot --output /absolute/path/to/local/source-quality.json
```

Канонический набор остаётся автономным. В окружении с уже установленной версией
proxy-scraper есть отдельная интеграционная проверка закреплённого API (без сети):
`python3 -B tests/library_pinned_integration.py`.

## Изолированный Chrome

### Чистая установка первого stable

`tests/fresh-install.mjs` проверяет ZIP в новой папке с пробелами, без готовой
`.venv`, настроек и истории. Запускается настоящий `Install.command` с явными
тестовыми `--profile`/`--data-dir` и установкой зависимостей. Native Messaging
registration и helper после установки не подменяются. Требуются сеть для
зависимостей и одного поиска адресов, Python 3.11+ и Chrome for Testing.

```sh
python3.14 scripts/package.py
TEST_PYTHON=/absolute/path/to/python3.14 TEST_INSTALL_ZIP=/absolute/path/to/country-proxy-1.0.0.zip node tests/fresh-install.mjs
```

`TEST_PYTHON` обязателен и задаёт абсолютный путь к Python 3.11+ для проверок архива; `PLAYWRIGHT_MODULE` —
внешний Playwright. Сам `Install.command` получает обычный PATH; проверки не
подменяют HOME и не используют `.venv` разработчика. Developer mode включается
в UI; выбор папки расширения автоматизирован через CDP `Extensions.loadUnpacked`.
Системный диалог выбора папки и macOS Gatekeeper этим не проверяются.

Первый запуск идёт через popup: равноправная группа NO/EE/AT, публичный поиск
до 120 секунд, затем Stop и restart с сохранением настроек. Публичная доступность
PASS/INCONCLUSIVE отделена от установки: отсутствие адреса не скрывает ошибку
helper, управления маршрутом или отключения. Нет подставных proxy/GeoIP/TLS,
изменения product timers или повторов поиска до успеха. Отчёт, логи установки
и обезличенные screenshots остаются в исключённом из Git `.runtime`.

### Другие браузерные сценарии

Нужны Playwright с Chrome for Testing и зависимости помощника. Установку зависимостей
выполняйте в отдельной копии только при необходимости сетевых тестов:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
```

Для `Install.command` в тесте обязательны точные `--profile` и `--data-dir`:
без `--profile` установщик регистрирует помощник основного Chrome.
Следующие стенды сами создают одноразовые профили и
Native Messaging registrations; основной Chrome им не нужен:

```sh
node tests/failover-lab.mjs
TEST_RESERVE=1 TEST_IDLE_FAILURE=1 node tests/failover-lab.mjs
TEST_RESERVE=1 TEST_RESTART=1 TEST_FAILURE=route node tests/failover-lab.mjs
```

Если Playwright установлен вне проекта, задайте `PLAYWRIGHT_MODULE` абсолютным
путём к этому модулю. Не добавляйте машинный путь в код. Перед тестом сравниваются
реально исполняемые background/controller/probe scripts с файлами на диске.
Стенд использует настоящий HTTPS и фактическую страну тестовой сети. Два loopback
прокси имеют общий внешний IP: этот PASS подтверждает механизм, а не публичную пару.

Дополнительная приёмка того же кода:

```sh
node tests/route-truth-lab.mjs
node tests/route-truth-lab.mjs --reserve-diagnostics
node tests/control-cancel-lab.mjs
node tests/reserve-race-lab.mjs
node tests/history-lab.mjs
node tests/resilience-lab.mjs
TEST_MULTI_SOAK=1 node tests/resilience-lab.mjs
TEST_BASELINE_ROOT=/absolute/path/to/previous-bundle node tests/install-lifecycle.mjs
node tests/country-selection.mjs
node tests/multi-country.mjs
TEST_STREAMING=1 node tests/multi-country.mjs
TEST_SOURCE_QUALITY=1 node tests/multi-country.mjs
```

`route-truth-lab` проверяет смену владельца прокси и восстановление выключенного
профиля. Второе распакованное расширение, регистрация помощника, HTTPS-сайты
и тестовый сертификат с отдельным ключом живут только в тестовой среде. Для
этого стенда нужны OpenSSL, Python 3, Playwright и Chrome for Testing с поддержкой
CDP `Extensions.loadUnpacked`. Внешние списки и реальный GeoIP не используются.

`control-cancel-lab` задерживает browser CONNECT и проверяет отключение и смену
страны. В `reserve-race-lab` соревнуются два резерва. В `history-lab` отказ
сохраняется при перезапуске профиля, затем восстанавливается HTTPS через тот
же адрес после истечения реальной минутной паузы. `resilience-lab` работает
не менее 30 минут и включает повторные отказы прокси, помощника и источника.
С `TEST_MULTI_SOAK=1` он выбирает три равноправные страны, затем меняет набор
и проверяет удаление недоступного резерва и его возврат при здоровом активном
соединении. Оба режима используют собственный headless-профиль и оставляют
отчёт в каталоге запуска внутри `.runtime/acceptance-20261030/soak/`.

Стенд `install-lifecycle` создаёт собственную копию,
venv и профиль, запускает настоящий установщик для старой/новой/старой версии,
сохраняет настройки и проверяет исполняемый код после Reload. Baseline читается,
но не изменяется; можно задать `TEST_PYTHON` для создания изолированного venv.
Установочный тест загружает зависимости из `requirements.txt` и требует сети.
Стенд `country-selection` проверяет полный каталог, поиск, отсутствие подключения
от ввода/избранного, сохранение пустого избранного при работающем соединении и
переход со старых настроек. Он сверяет исполняемые popup/options scripts и проверяет
обычный HTTPS через тестовый прокси. Это не проверка доступности всех 249 стран.
`multi-country` проверяет явное применение трёх равноправных стран, черновик без
переключения, общий резерв и физический отказ, восстановление набора после
перезапуска и отклонение реального выхода вне набора. Стенд использует настоящий
HTTPS/GeoIP одной тестовой сети: это не живая межстрановая пара. Переходы между
разными странами и отсутствие предпочтения текущей покрыты детерминированными
native/controller tests. Не подменяйте GeoIP ради заявления о live-переходе.

Публичная проверка выполняется отдельно и ограничена по времени:

```sh
TEST_COUNTRY=NO TEST_RESERVE=1 node tests/failover.mjs
```

Для тридцатиминутной проверки равноправной группы AT/EE/NO без публичных
прокси используйте `node tests/resilience-group-local.mjs` с `TEST_PYTHON`
и `PLAYWRIGHT_MODULE`. Стенд использует локальные HTTPS-ответы с известными
странами, штатные интервалы и отдельный Chrome. Смена выхода в этом сценарии
проверяет алгоритм; к доступности реальных публичных адресов она не относится.

Для проверки раннего отказа в изолированном Chrome запустите
`node tests/route-truth-lab.mjs --early-verdict`: один контрольный HTTPS-запрос
зависает, второй получает 503. Стенд проверяет адресный отказ, отмену соседа
и открытие обычной вкладки через следующий маршрут.

Для равноправной группы запустите `TEST_COUNTRIES=AT,EE,NO node tests/public-group-failover.mjs`.

Для сравнения ёмкости пополнения выполните один и тот же
`tests/refill_capacity_benchmark.py --root <snapshot> --output <report.json>`
через Python 3.11+ для сохранённого baseline и кандидата. Стенд использует
искусственные задержки, настоящий планировщик и по 20 повторов; проверяет
не только время приёма резервов, но и покрытие, отмену и лимиты. Его результаты
не являются измерением публичного HTTPS. Harness/config SHA должны совпадать.

Поддержание после единичного SOCKS-сбоя проверяет
`node tests/reserve-maintenance-lab.mjs` в отдельном Chrome for Testing.
Он использует реальные локальные SOCKS5/HTTPS-соединения, штатную maintenance
через 30 секунд и два физических отказа. Те же `TEST_PYTHON` и
`PLAYWRIGHT_MODULE` применимы. Для сопоставления старого кода запустите этот же
стенд с `TEST_CASE=success TEST_SOURCE_ROOT=<baseline>`; эталонный старый код
должен потерять резерв. Без `TEST_CASE` проверяются также TLS, HTTP, страна,
trace, зависший обязательный контроль, Stop и смена группы. Отчёты сохраняются
в отдельной временной папке `cp-reserve-maintenance-receipt-*`.

Для primary timeout используйте `node tests/reserve-timeout-lab.mjs` с теми же
переменными окружения. Реальный SOCKS primary истекает по прежнему connect30;
уже работающий дополнительный запрос получает ответ после наблюдения curl28.
Статусы и HTTPS-ответы не подставляются. `TEST_CASE=success` проверяет две
физические замены и первую admission C после подтверждения B; остальные cases
совпадают по именам с maintenance-стендом и проверяют отказ/отмену. Тот же
неизменный harness с `TEST_SOURCE_ROOT=<baseline>` должен воспроизвести прежнюю
потерю резерва. Отчёт — `cp-reserve-timeout-receipt-*`, с hashes источников,
реальными curl limits и очисткой временного профиля.

Пополнение после первой замены и второй отказ проверяются отдельным сценарием:

```sh
TEST_COUNTRIES=AT,EE,NO node tests/public-refill-failover.mjs
```

Отчёт дополнительно связывает physical probes с первым владельцем, ролью,
offer и непрозрачными endpoint/host/exit IDs; coalesced callers и неизвестная
атрибуция не подменяют владельца. После естественного снятия B без нового
резерва строгий результат сохраняется, а autonomousRecovery отдельно наблюдает
до 150 секунд в исходном общем deadline и лимите 360. Он не вооружает второй отказ,
не сбрасывает бюджет и не превращает discovery/возврат старого A в fresh-pool PASS.


Он ждёт первое подключение с резервом до шести минут, проверяет автоматическую
замену, затем до шести минут наблюдает новое пополнение после подтверждения
маршрута браузером. На каждую из двух замен отводится 150 секунд. Общий лимит
360 физических проверок адресов не сбрасывается между этапами. Каждый тестовый
health-отказ связан с конкретными сессией и предложением помощника.

Для второго отказа нужен живой адрес, чей host/exit впервые успешно принят в
резерв после подтверждения B; счётчика `pool.count` недостаточно. Для строгого
PASS обе замены идут через pool, а C принадлежит любому из подходящих новых
admissions до второго отказа B. Maintenance и повторный приём старого host/exit
не считаются новым адресом. Старый резерв, новый поиск или возврат на A после
карантина могут законно восстановить соединение; эти исходы фиксируются отдельно
и не дают строгого new-address PASS. От A/B должны отличаться и сервер, и выход;
все выходы остаются в выбранной группе. Старый резерв искусственно не исключается.

Диагностика сохраняет ограниченные журналы проходов пополнения, причин отсева,
новых добавлений и этапов отказа без адресов прокси. Исчерпание лимита проверок
или окна наблюдения означает INCONCLUSIVE, а не автоматически ошибку пополнения.
Публичные серверы не отключаются: отказы подставляются только в health-проверку
тестового помощника. Применяются отдельный профиль Chrome for Testing и обычные
HTTPS-проверки вкладки; основной Chrome не используется.
Тест создаёт отдельный профиль и регистрацию помощника. При внешнем Python с
зависимостями задайте `TEST_PYTHON`. До отказа требуются успешная обычная
HTTPS-вкладка и свежий резерв. Затем только тестовый помощник получает ошибки
проверки активного адреса. Обычная вкладка проверяет выход B.

Для диагностики отклонений на уровне HTTPS используйте отдельный тестовый профиль.
Локальный стенд воспроизводит сбой подключения к каждому из двух контрольных
хостов. Публичный стенд фиксирует результат каждой проверки помощника и связывает
браузерный отказ с конкретным запросом service worker. В отчёт попадают имена
двух контролей, статус HTTP, код сетевой ошибки и результат параллельного запроса.

```sh
node --test tests/https-probe-observer.test.mjs
node tests/route-truth-lab.mjs --https-diagnosis
TEST_COUNTRIES=AT,EE,NO node tests/public-https-diagnosis.mjs
```

По умолчанию тест ждёт подтверждённую вкладку и свежий независимый резерв.
Для отдельного опыта «что произойдёт, если активный адрес откажет сразу»
добавьте `--fault-on-first-tab`: A должен открыться в обычной вкладке,
но резерв при включении отказа не обязателен. В отчёте режим и фактическое
состояние резерва указаны отдельно. Нельзя складывать два режима в одну
долю успешных замен. Критерий для B и лимит времени одинаковы.

Публичный `public-group-failover` сохраняет в `report.json` журнал
`offerSessions` (поиск или резерв, возраст последней проверки резерва, решение
Chrome), `browserRejections` (HTTPS-запрос и код Chrome, если связь доказана),
`tabChecks` (исход загрузки обычной вкладки) и время имитированных отказов. Если к концу окна предложение ещё проверяется,
`pendingProbe` сохраняет видимое состояние каждого из двух запросов до
отключения профиля. Без однозначной связи результат остаётся неизвестным.
Подтверждение помощника, подтверждение расширения и открытие вкладки — три
разных события. Неполное наблюдение и непрошедшие окна учитывать отдельно.
Проводите сравнение в разных временных окнах, из неизменной копии в отдельном
профиле, с теми же лимитами и без ручной смены страны.

Для публичного стенда действуют те же `PLAYWRIGHT_MODULE` и `TEST_PYTHON`.
Итоговый JSON сохраняется в созданной стендом папке `.runtime/public-https-*/`.
Если первый прокси остаётся исправным, флаг `--sample-confirmed` переключает
до четырёх уже подтверждённых маршрутов штатной командой «Найти другой».
Такая смена фиксируется отдельно. Код `ERR_ABORTED` у второго запроса может появиться, когда расширение завершает
проверку после отказа первого. При разборе сверяйте поле `endpoint` в решении
расширения с `requestId` и `error` в данных DevTools.

Чтобы локализовать следующий `ERR_CONNECTION_CLOSED` именно у Cloudflare:

```sh
node --test tests/netlog-phase.test.mjs tests/netlog-projection.test.mjs
node tests/netlog-phase-lab.mjs
TEST_COUNTRIES=NO,EE,AT node tests/public-https-diagnosis.mjs --netlog
```

Локальный стенд разрывает соединение в трёх известных точках и сравнивает
наблюдение со стороны Chrome с тем, что успел получить сервер. Публичный режим
ждёт до 8 минут (до 480 проверок на всю группу и до 8 ручных смен уже
подтверждённых маршрутов). Ручная смена не засчитывается как отказ. Остановка —
при первом адресном отказе Cloudflare с нужным кодом. У Chrome включён стандартный
[NetLog](https://www.chromium.org/for-testers/providing-network-details/),
проверка сертификатов штатная. Сырой файл обрабатывается локально после закрытия
тестового браузера и удаляется вместе с временным профилем. Для сопоставленного
отказа остаются обезличенные события и вывод в `observations.json`.
Смежные первичные ошибки Cloudflare сохраняются отдельно и не закрывают критерий.
Для дополнительного короткого окна укажите `--netlog --short` (6 минут, 360
проверок, до 4 смен). Если точный отказ
не повторился или фазу нельзя доказать, результат — `INCONCLUSIVE` (код 2).

В одиночном сценарии страна — параметр. `PASS` требует разных host/выходных IP и обычной HTTPS-вкладки
до/после отказа. `PARTIAL_NO_ALTERNATE` или `INCONCLUSIVE`, exit 2, не считаются PASS.
Нехватку бесплатных адресов записывайте в результат; не ослабляйте TLS/GeoIP ради теста.

Расширенный smoke `tests/integration.mjs` и восстановление `tests/recovery.mjs`
используют постоянный **тестовый** `.runtime/chrome-test`. Только для них сначала:

```sh
python3 scripts/install.py --profile "$PWD/.runtime/chrome-test" --data-dir "$PWD/.runtime/test-history"
```

`TEST_SAVED_PROFILE=1` у lab тоже требует этой подготовленной регистрации.
`TEST_RESTART=1` без него достаточно для повторного запуска одноразового профиля.
Никогда не подставляйте user-data-dir основного Chrome. Сырые отчёты и снимки
остаются в игнорируемой `.runtime/`; краткий результат — в `docs/verification.md`.

## Изменение и PR

1. Опишите конкретное поведение до и после; добавьте регрессию для исправляемого сбоя.
2. Обновите нужные пользовательские документы и раздел `Unreleased` в CHANGELOG.
3. Выполните контракт. Для proxy/controller/session/installer выполните применимые
   изолированные сетевые и update/rollback сценарии.
4. Откройте PR с результатами и ограничениями. Публикуйте краткий проверяемый
   итог; сырые логи и профили в PR не прикладывайте.

`main` содержит прошедший review код. Выпуск — отдельный тег и Release по
[процедуре](releases.md); архив из рабочей ветки выпуском не является.

## Что документировать

В repo храните актуальное поведение, команды воспроизведения, технические решения
и ограничения конкретной версии. В [verification](verification.md) достаточно
версии, даты/среды, сценария, результата и его границ. Историю рабочих сессий,
личные действия в браузере и локальные административные процедуры сюда не добавляйте.
Цели, приоритеты и планы ведутся в базе знаний проекта; технические инструкции
не дублируются там целиком. Сырые evidence остаются вне Git.
